## 2. Reachability after C

Three different situations must stay separate:

1. **Internal legacy references:** eight helper functions are now referenced only by other helpers in the old graph. They have no direct dispatcher entry. Removing one in isolation while leaving its callers would still be an incomplete cleanup.
2. **Textual dispatcher references, intercepted under supported configurations:** seven helpers still appear in the late dispatcher. Earlier current-flow handlers or rejection guards return before those call sites. This is stronger evidence after B's mode matrix, but the dispatcher needs a separately reviewed equivalent rewrite before retiring those references.
3. **Active compatibility and recovery:** current rejection messages, Menu/human support, `booking:`/`change:` journal actions, stored receipts/continuations and reminder/inbox compatibility remain operational. Their old-looking state names do not justify deletion.

## 6. Existing evidence and additional tests for a future rewrite

B already added 417 tests and C kept them all. Its 16 supported configurations and 1,728 grouped historical-state inputs materially strengthen the audit. The tests also cover genuine request creation, valid historical decisions, foreign ownership, new-customer validation, persistence and uncertain recovery. The owner has now accepted the complete C PC checklist as well. This evidence supports planning the next cleanup; it is not an exhaustive equivalence proof for a different dispatcher.

Before any later Category B implementation, add the smallest relevant tests in a separate reviewable test commit:

1. **Exact behavior comparison:** compare C and the proposed dispatcher on the same synthetic inputs, including scoped session deletion/retention, journal states, outbound message text/order, Calendar read/write traces and duplicate suppression. Normalize only generated IDs. B's broad rejection regex assertions do not prove every rejection copy/ordering detail would survive a rewrite.
2. **Old text selectors across modes/restarts:** explicitly combine `1`/out-of-range numbers and `si`/`sí`/`no` with each old selection/registration state, expiry, known/new identity and restart. Existing support-only tests cover numeric/affirmative text; B's full mode matrix uses `Nombre Prueba` for its generic text cases. B restarts a legacy registration state and current choices, not every historical shape through every restart/transport combination.
3. **Every journal action's accepted shape:** preserve booking's button-only journal route and intentional list rejection; preserve management's existing button/list support. B exercises valid change `yes` via button, `no` via list, retry via button and status via list, rather than every decision × every shape. Invalid/foreign/expired journal cases must still fail without writes.
4. **Current navigation and malformed/stale inputs:** ensure human-menu tokens, unknown list/button IDs, main-menu free text, natural-intent clarification, date/name entry, unsupported message types and expired session shapes keep their current priority and outcome. Do not move global Menu, human chat or signature/deduplication boundaries while simplifying old arms.
5. **Active reminder context where relevant:** B's added off/dry-run/live compatibility configurations do not activate a reminder business. Existing reminder tests separately cover real enrollment/permissions/templates. If a dispatcher rewrite touches shared precedence, couple old inputs with an enabled synthetic business, genuine permission evidence, due jobs, stale/current reminder tokens and quoted replies; no live Meta/Google calls.

These are requirements for the proposed future transformation, not newly found failures in owner-accepted C. No new tests or test changes are made in D, and no production data should be collected to build adversarial fixtures.
