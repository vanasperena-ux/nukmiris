All four names and `es_MX` already matched the owner's report; no name/copy/flow remapping was needed. Variables remain **scoped customer full name, business name, full local Spanish date, `HH:mm`**. Confirmation/follow-up indexes `"0"` and `"1"` carry `reminder:<UUID>:confirm` / `reminder:<UUID>:reschedule`. Existing signed `button.payload` callbacks bind to the correct business/customer/current appointment schedule.

The original verifier already checked actual WABA/sending-number membership and required `APPROVED`, `UTILITY`, exact name/language/body/button contract and explicit safe TTL at startup and before every send. Active quality pending is eligible if the API returns that approved contract. A default/null/30-day TTL remains unsafe: maximum accepted custom TTL is 900 seconds for the first three and 300 for final, with a minimum of 30. Status/category changes, mismatches or unavailable assets block sends. No cached approval, per-send TTL invention or proactive free-form fallback was introduced.

Identified gaps were operational and one reliability defect:

1. The previous dispatch catch could make a thrown send or failed accepted-result persistence retryable, even after possible Meta acceptance.
2. Ordinary live mode could process every enabled business's jobs, without a test-recipient/appointment restriction.
3. Status output lacked accepted job IDs/message IDs and attempt history needed to distinguish acceptance from delivery.
4. Template checks stopped at the first mismatch and did not explain the mismatched contract field.
5. Documentation still treated the assets as awaiting submission/approval and lacked a safe accelerated PC procedure.

## Established policies and ambiguities resolved without silent changes

- Reminder offsets are elapsed hours, not local-clock day arithmetic. Business timezone still controls appointment date labels/variables.
- Enrollment requires a verified new booking after business activation, with strict-future due times. No existing/untracked import. The existing intent-creation versus activation comparison is unchanged.
- Submission allowance is due through 15 minutes late, before start, with template TTL plus transport budget fitting before start. Late work is skipped; this is not a device-delivery deadline.
- A follow-up processed without delivered/read parent proof is skipped permanently, even if proof later arrives within the allowance. This task documents, rather than changes, that established behavior.
- Confirmation suppresses follow-up, not final. Nonresponse never cancels. Reschedule response preserves the original/final and suppresses a claim that the customer never responded.
- Unknown sends/recovered `sending` jobs remain uncertain. Accepted-but-undelivered is not safe to resend; delivery failure is retained for review. Signed delivered/read evidence cannot be downgraded by later timeout/failure.
- Historical visible reminders can make generic replies ambiguous; use the exact current button/quote. TTL does not erase visible messages or permit retargeting old replies.
- Test restrictions hold other jobs without incrementing attempts or expiring them. Normal enrollment/booking continues; receipt evidence/restart uncertainty can still be recorded. Removing restrictions while live broadens processing and requires a separate explicit owner decision.

## Configuration and manual verification boundary

New optional values, all blank by default:

```dotenv
NUKMIRIS_REMINDER_TEST_BUSINESS_ID=
NUKMIRIS_REMINDER_TEST_RECIPIENT=
NUKMIRIS_REMINDER_TEST_BOOKING_ID=
```

Set all three to the existing test business, exact registered sender and selected booking before live test activation. Existing `NUKMIRIS_REMINDERS_MODE=off|dry-run|live`, poll interval and capability gates retain their meanings. No global reminder intervals, credentials, real environment variables or database settings were changed during implementation.

PC verification requires the owner to supply local provider access and an explicitly authorized recipient, run the all-four asset check, record genuine permission and execute the restricted plan/apply/start sequence. Check real WhatsApp arrival, signed delivered/read callbacks, the selected Google event and restart behavior. Record that evidence before calling live validation complete. See the guide for every exact command and expected observation.

Remaining limits: owner-supplied approval has not been independently observed; safe TTL/content/WABA/token checks can still fail; PC/tunnel uptime is necessary; delayed/missing delivery may intentionally suppress follow-up; unknown outcomes may need review. Manual external Calendar edits can race the final send check. Local singleton/one-database coordination is preserved, not upgraded to multi-host operation. Reports contain scoped local customer/provider identifiers and are not a public redacted dashboard.

**No automatic merge, live send, provider configuration update or architecture implementation is part of this task.** Owner PC/live results must be appended as a separate verification record after testing; the current accepted baseline remains v0.8.1.
