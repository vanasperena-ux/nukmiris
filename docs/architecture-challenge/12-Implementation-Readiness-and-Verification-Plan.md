## 1. Rebuild versus rearchitecture: final design recommendation

**Recommend C — new greenfield application, with deliberate reuse of v0.8.1's tested domain knowledge.** This is an engineering-direction decision, not a claim that an unbuilt application is safer or authorization to replace the POC now.

The changed evidence is the convergence of two needs. First, the combined safety contract changes acceptance durability, operation/attempt ownership, dispatch, tenant identity and restore. Second, confirmed future requirements introduce employee resource capacity on one Calendar, manual-event adoption/consent trust and participant-aware native WhatsApp routing. These cross the same persistence and orchestration boundaries. No production migration or obsolete state/button compatibility is required. The owner values coherence and long-term reliability over minimizing the first diff. A fresh core can establish those boundaries once while using the accepted application as a behavioral oracle.

| Criterion, same P0 scope and quality gates | A Retain/improve | B Selective rearchitecture | C Greenfield |
| --- | --- | --- | --- |
| Architectural coherence | New protocols embedded in legacy transaction/dispatcher organization. | Coherent if seams are final; risk of a permanent hybrid when nearly every safety boundary changes. | One explicit state/transaction/identity model from first slice. Must demonstrate coherence in code. |
| Functional correctness | Existing covered paths preserved; changed safety paths still need proof. | Preserves useful semantics, but seam transitions can break continuation/finalization. | Full parity reconstruction risk; pure rules and acceptance cases reduce it, not eliminate it. |
| Reliability under failure | Cross-cutting admission/archive/dispatch changes are substantial even if files stay. | Two authorities during transition are a special hazard. | Can design one authority; every crash/uncertainty behavior must be re-proven. |
| Security | Add commercial scope/secret/operator controls around existing model. | Replace trust boundaries deliberately; retain verified predicates. | Build scoped relationships/origins/roles together; privileged mistakes remain possible. |
| Maintainability | Attractive only if coupling remains manageable under new features. | Potentially sound, but retaining little runtime makes B essentially C with transitional baggage. | Best fit to the selected direction if clear modules and modest abstractions survive real changes. |
| Testability | Valuable current fixtures; new DB/admission/recovery cases still needed. | Adapt tests at each replaced boundary and test transition. | Requirement-based suite from day one; actual DB/concurrency/restore tests mandatory. |
| Development/operations effort | Lower first change, not necessarily lower complete cost. | Can reduce work only if a measured stable seam avoids replacement. | Larger initial parity effort; no migration overhead. Operations/security costs are common to all. |
| Long-term scale | Existing single-owner topology can serve a constrained pilot; not proof of target platform. | Can add managed topology, but execution ownership must remain unambiguous. | Separate ingress/workers possible; no capacity claims before measurement. |
| Future requirements | Calendar locks/customer-creation assumptions need broad changes. | Staff/manual/native-chat seams cut across much of the retained core. | Explicit resource, origin, consent and participant foundations accommodate deferred workflows. |
| Regression/cutover risk | Frequent smaller regressions in an active working codebase. | Highest dual-model transition burden if undertaken in-place. | Isolated candidate protects POC; broad parity/operational acceptance required before cutover. |

This does not use line count or undocumented numerical quality scores. A well-evidenced stable seam could still reduce the work under C by porting code. No full second implementation of B is required before action: the first safety slice is a stop/go gate. If it disproves the assumed benefit or reveals unmanageable cost, return a concrete revised plan to the owner, not silently proceed with a full rewrite.

## 6. Effort, operating model and uncertainty

Planning assumptions: an experienced full-time Node/SQL implementer, available independent code review, maintained provider simulators and owner access to test accounts. AI assistance may improve drafting; it does not remove engineering verification, account approvals, support or legal work. The first scope contains no complete dashboard/catalog/billing/native-chat/manual import/multi-employee UX. No legacy migration compatibility budget is included.

A preliminary **20–40 engineer-week envelope** for parity, safety and launch evidence is a planning hypothesis, not an approved budget or delivery date. It includes review/rework and operational drills; provider/owner/legal elapsed waits are additional. Allocate an initial bounded scope/protocol/safety-slice stage, roughly **3–6 engineer-weeks**, then replace the envelope with a bottom-up estimate from demonstrated code. Failure of the core proofs may require stopping or changing deployment assumptions. These figures do not supersede owner budget approval and are not directly comparable with the earlier unequal estimates. Future workflows need separate estimates after their policies and provider capabilities are established.

Recommend managed always-on application roles and managed PostgreSQL as a candidate operational direction, with independent recovery evidence/key custody and redacted telemetry. Instance count, HA tier, region, retention, archive format, recovery objectives, alerts/on-call and monthly cost remain undecided. Validate no-loss arming promotion or choose fail-stopped recovery; a cheaper degraded tier cannot retain an unproven HA promise. Price compute, DB/standby, evidence/backups, keys/secrets, telemetry, provider charges, test/canary accounts and support time. Meta payer/billing remains open; Tech Provider status does not alone assign the invoice.

## 7. Go/no-go for replacing the accepted application

**Go only when all applicable conditions hold:**

- Exact candidate source/environment are recorded; all original parity requirements and amended safety gates pass, independently reviewed in actual code.
- No critical unknown permits an unauthorized event/send, duplicate possible automatic attempt, employee conflict, consent revival, cross-tenant effect or unsafe restored dispatch. Conservative unavailability is explicit, observable and operable under the agreed policy.
- Provider accounts/permissions/templates and actual WhatsApp callbacks/Calendar changes are verified with authorized recipients; the owner repeats ordinary/new-customer/date/management/human/restart tests. Future claims require their feature-specific acceptance, not P0 tests.
- Targets, privacy/retention/custody, staffing, costs and operator risk-release authority are approved; chosen deployment/restore/rollback proof matches those claims.
- Cutover inventories outstanding v0.8.1 accepted work/effects, quiesces old admission and dispatch, and resolves or holds uncertainty before candidate authority. No historical data migration is required, but outstanding effects cannot simply be forgotten.
- Candidate starts with controlled receiving scope and reminders disabled until explicitly enabled. There is one external dispatch authority per affected resource. Code rollback preserves candidate journals and armed evidence; restoring an old DB is not rollback of Google/Meta effects.
- The owner explicitly authorizes replacement/activation. Preserve a protected reference checkout/tag and operating evidence; no automatic main merge.

**No-go:** any missing mandatory proof, ambiguous permission/customer/resource mapping, incomplete recovery gap with resumed effects, unresolved critical review finding, failed provider capability needed for the promised product, or unavailable operational/privacy approval. A narrower supervised pilot requires an explicit scoped operating contract; it cannot silently waive core safety/tenant invariants.

The architecture direction is now established: fresh implementation, parity first, known future identities designed in, workflows expanded deliberately. The next owner-approved prompt should authorize only the named initial packages, tools, environments and proof gates. This review completes the design assignment; it does not start WP0, install dependencies, run experiments or modify the application.
