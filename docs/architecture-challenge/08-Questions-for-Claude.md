# 08 — Questions for Claude, Round 2

These are technical proof requests, not a request to defend the author or prefer a technology. References C1–C5 use the five original PDFs identified in [06](06-Codex-Peer-Review-of-Claude.md#source-key). Each question could change the recommendation. Please answer with an enforceable invariant, failure trace, correction or explicit unresolved limit; passing a simulator written to the assumption is insufficient provider evidence.

1. **What exactly guarantees same-ID insert safety?** C1 F-03/S-1 (pp3–4,9), C2 §§8.4/9.2 (pp19–22), C3 ADR-006/009 (pp4–6), C4 scenario 3 (pp3–4). The official Google generated declaration warns collisions may not be detected at creation. A's timed-out insert is invisible, B retries the same ID after ten minutes, A later completes: what documented guarantee prevents duplicate effects? Include tombstones, delete-before-late-insert and ID reuse. Would you retain read-only uncertainty until that guarantee exists?

2. **How is a paused external dispatcher fenced?** C2 §§4.2–4.3 (pp8–9), §8.4 (p19), C3 ADR-004/008, C4 scenarios 4–5 (pp4–5). A commits a submission marker and pauses before HTTP; B claims the expired lease; A resumes. SQL fence rejection happens after the provider call. Which nontransferable submission permission prevents stale external execution, and when may another dispatcher submit? Include multiple loops in one process and an old host not known dead.

3. **What completes the exclusion constraint's proof?** C2 §8.2 (p17), C3 ADR-008 (p5), S-10. Two different operations use the same appointment key and overlapping source/target intervals: `appointment_key <>` is false, so both reservations are allowed. Show DDL/FKs/admission transitions enforcing one unresolved mutation of that event, including attendance/cancel, NULL/empty ranges, buffer and rollback. Which expired protections can be released, and what evidence permits releasing an uncertain write?

4. **Why is five-minute uncertain-order advancement acceptable?** C1 F-05 (p4), C2 §10.1 (p22)/§9.2 (p21). Earlier send A remains possibly deliverable when B is released. A later arrives after B with contradictory/stale instructions. Which baseline requirement permits that relaxation? Distinguish an unsent expired prompt from an uncertain attempt. Would you preserve the barrier or request a changed customer contract?

5. **How can generic confirmation safely ignore old requests?** C1 U-GENERIC (p7), C2 §11.4 (p26). A reminder for the old schedule arrives after a move and after the sole current B request. The customer's unquoted “Sí” answers A. Why does exactly one current candidate identify intent? Please reconcile with baseline R12 and retained accepted/uncertain historical requests, or require exact current buttons/quotes.

6. **How are lost attempt/operation identities reconstructed during restore?** C2 §§16.3–16.4 (pp38–39), C4 scenario 10 (pp9–10), C5 G4 (p5). A post-snapshot customer message is archived, but the random operation/event ID and outbound attempt allocated afterward are lost; no receipt exists. Replay can allocate new IDs. What evidence prevents a second event/message/reminder, and how do you discover unknown scopes? Quarantine must include Calendar writes and old instances, not only sends.

7. **What atomically preserves withdrawals and operator mutations outside the failed database?** C2 §5.1 (p9)/§16.3 (p39), C3 ADR-018 (p8), C4 p10. STOP or operator revoke commits and is acknowledged, but the primary fails before best-effort archive export. An operator command journal is another dual write. Define archive completeness/gap detection, acknowledgment boundaries and suppression on missing evidence. Can T-4's two-hour write resumption coexist with zero lost withdrawals, or must it remain blocked?

8. **How does permission withdrawal win during slow preflight?** C2 §11.3 (pp25–26)/§11.5 (p26), C4 scenario 5 (p5). A checks permission, waits on template/Calendar reads, while STOP is durably accepted. Before A sends, where is withdrawal serialized with final admission? An inbox row awaiting mailbox processing does not alone suppress A. Include token revocation and status/TTL changes in the same failure reasoning.

9. **What is the complete customer/event ownership predicate?** C1 F-04 (p4), C2 §7.2 (p14)/§12.2 (pp29–30), C4 scenario 7 (pp6–7). `nm_biz` matches, but customer A supplies customer B's known event ID in the same business, or an authorized Calendar client copies properties. Which trusted local identity/operation/customer checks are mandatory? Private extended properties are not an authorization boundary by themselves.

10. **What prevents selecting arbitrary RLS tenant context?** C2 §12.2 (pp29–31), C3 ADR-012 (pp6–7). Can `app_runtime` run `SET LOCAL app.business_id` for B? If yes, what does RLS protect against, and what does it not protect against? Show ownership/grants/search_path for privileged discovery functions, pooling reset tests, multitenant raw-batch access and per-business operator grants. How is break-glass audit enforced if its role can bypass ordinary restrictions?

11. **How are reschedule availability and synchronization complete?** C2 §§7.3–7.5 (pp14–15), ADR-007/014 (C3 pp5,7), S-3/S-4. A free/busy response can merge the moving event with another busy event, so subtracting its old interval can hide another reservation. What complete event-aware query checks the target? If `nm_biz` is removed or a deletion tombstone lacks properties, how does filtered `updatedMin` sync detect it? Specify pagination and cursor advancement atomically.

12. **Which deviations from baseline conversation/reminder policy are intentional?** C1 U-NAME/U-COMMAND (pp6–7); C2 §§5.4/6.4/11.3 (pp10,12,25); C4 scenarios 5/8 (pp5,8). Only Menu overriding name entry, poison-event skipping, expired-name input through Main and waiting for late parent delivery differ from current evidence or across your documents. Which require owner approval, and what exact acceptance cases change? Confirm current template TTL caps and transport-before-start budget remain enforced.

13. **What durable commitments survive HA failover and deployment rollback?** C2 §§14/16 (pp33–39), C4 scenario 4 (p4)/11 (p11), C3 ADR-016/018. A marker committed on the old primary authorizes a remote send, then failover loses that marker. A replacement sees pending/unsubmitted work. What replication/dispatch admission contract prevents replay? Define quiescence, schema/version compatibility, rolling worker overlap and credential cache invalidation; “every step is restartable” is insufficient for armed effects.

14. **How do privacy and recovery obligations coexist?** C1 F-12/T-7 (pp5,8), C2 §§13/16 (pp31–39), C3 ADR-013/018. What data is immutable, where, for how long, with what erasure/key policy? How are external Calendar PII copies and lost revocations handled? Please distinguish encrypted database theft from runtime compromise with KMS access, and specify operational custody/retention of archived command/evidence payloads.

15. **What evidence makes a rebuild preferable at equal scope and cost?** C5 §§5–9 (pp3–7), T-1–T-7, original Codex 05 §10. No production migration is required, which favors a clean core; existing failure scenarios remain valuable. Compare A/B/C using the same parity/security/recovery gates, a representative change and operator incident exercise, complete staffing/cloud cost and measured workload. Which experiment would make you choose selective rearchitecture instead? What would invalidate the proposed 10× headroom, seven-to-ten engineer-month range or small-team on-call assumptions?
