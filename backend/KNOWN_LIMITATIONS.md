Remaining limits:

- The owner confirmed the v0.1.0 availability integration, reported the v0.2.0 automatic-booking PC checkpoint successful, accepted the v0.2.1 menu update, and confirmed successful v0.3.0 rescheduling/cancellation on 2026-10-24. The cloud agent has no direct PC access; its tests use synthetic data/simulated services. Separate live results for each concurrency and crash-recovery case were not supplied, so the limits below still apply.
- The owner subsequently verified v0.3.1 (“OK I tested v0.3.1 all good thanks”) and completed the requested v0.4.0 saved-choice/post-selection/support restart and backup/isolated restore checks. Exact crash timing, each transport-failure case, and 24-hour backup scheduling/retention are not independently established by that report; offline tests and the limits below remain relevant. New customers still need one valid name. Repeated current selections reuse the saved request; stale selections after another flow are rejected. Menu appointment details reuse the existing lookup in connected booking mode; read-only/support modes retain their narrower authorization.
- Durable delivery requires explicit preparation and `NUKMIRIS_ENABLE_RELIABILITY=true`; with the flag off, message queues/deduplication still live in memory. Reliability mode retains message history for deduplication and does not yet purge it automatically. One local worker owns the database; there is no coordination between independent database copies or distributed hosts.
- An unknown Meta send result does not establish whether the customer received the reply. Matching signed Meta status callbacks can resolve uncertainty; otherwise it remains for operator review. Explicitly retrying an uncertain saved reply can duplicate WhatsApp text, while Calendar operations continue using their existing request identity. Known transient API rejections retry with backoff. Old interactive prompts/customer-service-window replies expire rather than being sent late.
- Automatic backups are local, consistent SQLite snapshots verified before retention pruning. Restoring an older snapshot can lose work accepted since it was created and does not undo Google events. Backups exclude `.env`/OAuth files; disk/device loss can affect both the working database and local backups. The restore command creates a separate unused file and never replaces the configured live database.
- One shared test Meta token and Google account are used for this development checkpoint. Real owner onboarding, independent credentials, tenant authorization, and offboarding are not implemented.
- Availability authorization stays separate. Optional booking consent adds `calendar.events`, covering new appointments and, when separately enabled, scoped rescheduling/cancellation. Existing grants are not revoked or replaced.
- New bookings require `NUKMIRIS_MODE=booking`, receiving-number routing, prepared journal tables, separate booking authorization, and an explicit customer slot selection. Management additionally requires `NUKMIRIS_ENABLE_MANAGEMENT=true` and its prepared change journal. It defaults to disabled and supports only upcoming, nonrecurring events created by this booking service and still carrying matching ownership metadata; manual/legacy events are not imported.
- Google offers no atomic availability-check-and-write operation. Local locks/journal checks prevent overlapping participating app requests, but a simultaneous manual edit or another app can race with insertion or movement. ETags protect edits to the source appointment, not every event in the target time. This is not a production distributed booking guarantee.
- Ambiguous writes are never blindly retried. The app verifies the original event ID and expected outcome; unresolved outcomes retain the calendar lock until reconciliation/manual review. A missing event does not prove an ambiguous insert or move succeeded; it can establish that a requested cancellation's event is gone.
- Only same-day business hours are supported. The dynamic update searches 30 days initially, then 15 new days at a time for three available dates, with a separate maximum horizon of 365 days. The final date can be partial: appointments and buffers must finish by the current business-local time plus the configured number of calendar days. The old runtime `NUKMIRIS_LOOKAHEAD_DAYS` value is retired. Employee calendars and staff allocation remain future design work.
- A fully booked year requires up to 24 sequential range requests (plus any event pagination needed for rescheduling). Each availability API request has a 15-second timeout; failures stop the search and produce an error, not a no-availability claim. No background scan or new availability cache is introduced. Session choices remain temporary snapshots and are rechecked before writes. A per-business policy override can be supplied through the existing service configuration boundary, but no business settings UI/persistence has been added.
- There is no owner dashboard/authentication or reminder worker yet. The architecture diagram remains a target, not a list of completed components.
- Bernard's unspecified buffer/break settings remain unspecified. Juanita's closing time, zero buffer, and hourly start interval were confirmed by the owner for this checkpoint.
